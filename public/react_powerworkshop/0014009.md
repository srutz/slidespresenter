# 14.9 Build, Deployment und Produktion / Source Maps und Fehleranalyse

## Source Maps

- Der Production Build ist minifiziert: Fehler zeigen `a.js:1:48213` statt `UserList.tsx:42`.
- Source Maps ordnen minifizierten Code dem Originalcode zu.

```typescript
// vite.config.ts
export default defineConfig({
  build: {
    sourcemap: 'hidden', // true | false | 'inline' | 'hidden'
  },
})
```

- `true`: `.map`-Dateien plus Verweis im Bundle, DevTools laden sie automatisch.
- `'hidden'`: `.map`-Dateien werden erzeugt, aber nicht im Bundle verlinkt: ideal für Error Tracking.
- Maps öffentlich auszuliefern macht den Quellcode lesbar; besser zum Error-Tracking-Dienst hochladen und nicht auf den Webserver legen.

# 14.9 Build, Deployment und Produktion / Error Tracking mit Sentry

- Dienste wie Sentry sammeln Fehler echter Benutzer mit Stacktrace (über Source Maps lesbar), Browser, URL und Release.

```bash
npm install @sentry/react
```

```typescript
// main.tsx
import * as Sentry from '@sentry/react'

Sentry.init({
  dsn: import.meta.env.VITE_SENTRY_DSN,
  environment: import.meta.env.MODE,
  release: import.meta.env.VITE_APP_VERSION,
  enabled: import.meta.env.PROD,
})
```

- Source Maps lädt man in der CI beim Build hoch (Sentry-Vite-Plugin `@sentry/vite-plugin`) und löscht sie danach aus `dist/`.
- Die DSN ist öffentlich, der Upload-Token ist ein Secret und gehört nur in die CI.

# 14.9 Build, Deployment und Produktion / Error Boundaries und Logging

- Error Boundaries fangen Render-Fehler im Komponentenbaum und zeigen eine Ersatzansicht statt einer weißen Seite.
- React 19 bietet zusätzlich `onCaughtError` und `onUncaughtError` an `createRoot` zur zentralen Protokollierung.

```typescript
import { ErrorBoundary } from 'react-error-boundary'

function logError(error: Error, info: { componentStack?: string | null }) {
  console.error(error, info.componentStack)
  // Sentry.captureException(error)
}

<ErrorBoundary FallbackComponent={ErrorPage} onError={logError}>
  <App />
</ErrorBoundary>
```

- Nicht abgefangen werden Fehler in Event-Handlern und asynchronem Code: dort `try/catch` und globale Handler (`window.onerror`, `unhandledrejection`) verwenden.
- Fehleranalyse im Browser: Console, Network-Tab (Statuscodes, fehlgeschlagene Chunks) und Sources (mit Source Maps).
