
# 22.6 SemVer und npm (Zusatzthema) / SemVer auf eigene Projekte anwenden

## Eine kleine Gedankenübung

- SemVer setzt eigentlich nur zwei Dinge voraus:
  1. Es gibt eine **öffentliche Schnittstelle**, auf die sich andere verlassen.
  2. Es gibt **Konsumenten**, die eine Entscheidung treffen müssen: "Kann ich gefahrlos aktualisieren?"
- Diese Voraussetzungen erfüllen weit mehr Dinge als nur npm-Pakete. Wo überall in einem typischen Projekt gäbe es eigentlich eine "öffentliche Schnittstelle", die von SemVer profitieren könnte?

## Kandidaten jenseits von "Bibliotheken"

- **Eigene REST-/GraphQL-APIs**: Ein neues Pflichtfeld in der Response ist meist ungefährlich (MINOR), das Entfernen eines Felds bricht Clients (MAJOR).
- **Interne Microservices**: Auch zwischen Team-Grenzen ist ein Vertrag über Kompatibilität wertvoll - selbst wenn nie ein "richtiges" Release gebaut wird.
- **Config- und Datenformate** (z. B. ein JSON-Schema, eine YAML-Struktur): Wird ein Feld umbenannt, ist das genauso brechend wie eine geänderte Funktionssignatur.
- **CLI-Tools und deren Flags**: Ein entferntes Flag bricht Skripte anderer Leute, genau wie eine entfernte Funktion eine Library bricht.
- **Datenbank-Migrationen / -Schemas**, **Terraform-/IaC-Module**, sogar **Design-System-Komponenten**: überall dort, wo jemand "gegen" etwas programmiert, ist die Frage "kompatibel oder nicht?" relevant.

# 22.6 SemVer und npm (Zusatzthema) / SemVer auf eigene Projekte anwenden

## Die eigentliche Erkenntnis

- SemVer ist im Kern kein npm-Feature, sondern ein **Kommunikationswerkzeug**: eine knappe, maschinenlesbare Antwort auf die Frage "Was habe ich kaputt gemacht?"
- Der Nutzen entsteht nicht durch das Format `X.Y.Z` allein, sondern durch die **Disziplin**, es ehrlich einzuhalten - eine falsch vergebene PATCH-Version ist schädlicher als gar keine Versionierung.
- Diskussion: Wo in euren eigenen Projekten gibt es bereits (unausgesprochene) Verträge, für die eine explizite Versionierung sinnvoll wäre?
