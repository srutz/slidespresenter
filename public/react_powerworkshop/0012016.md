# 12.16 State Management mit Zustand / Redux Toolkit: kurze Einordnung

## Wann Redux Toolkit?

- **Bestehende Anwendungen**: Redux ist weit verbreitet, Redux Toolkit (RTK) ist der offizielle, empfohlene Weg dafür.
- **Große Teams und Enterprise-Projekte**: feste Konventionen (Slices, Actions, Reducer), bewährte Patterns, viel Dokumentation.
- **Komplexe Side-Effects**: Listener Middleware, Redux DevTools mit Time Travel und Action-Log.
- **RTK Query**: Data Fetching und Caching im Redux-Ökosystem, vergleichbar mit TanStack Query. Sinnvoll, wenn Redux ohnehin im Einsatz ist.

## Vergleich zu Zustand

| | Redux Toolkit | Zustand |
|---|---|---|
| Einstieg | mehr Konzepte (Store, Slice, Provider) | ein `create`-Aufruf |
| Struktur | vorgegeben, einheitlich | frei, selbst zu definieren |
| Provider | ja | nein |
| Server State | RTK Query | TanStack Query (separat) |
| Neues Projekt | selten die erste Wahl | meist ausreichend |

# 12.16 State Management mit Zustand / Redux Toolkit: kurze Einordnung

## Migration und Empfehlung

- Neue Projekte: Zustand für Client-State plus TanStack Query für Server-State.
- Bestehende Redux-Projekte nicht ohne Anlass umschreiben. Wenn nötig, schrittweise: neue Features mit Zustand, alte Slices bleiben.
- Redux-Legacy (`createStore`, handgeschriebene Reducer, `connect`) auf RTK (`configureStore`, `createSlice`) und Hooks (`useSelector`, `useDispatch`) migrieren.
- Der Wechsel von Redux zu Zustand ist mechanisch: Slice wird zu einem Store, Reducer-Cases werden zu Actions mit `set`, `useSelector` zu Zustand-Selektoren.
- Die Konzepte (Selektoren, immutables Update, getrennte Server- und Client-Daten) bleiben gleich.
