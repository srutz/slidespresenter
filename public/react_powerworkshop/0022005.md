
# 22.5 SemVer und npm (Zusatzthema) / SemVer außerhalb von Node.js

## Ein sprachunabhängiger Standard

- SemVer ist keine Erfindung von npm oder Node.js - der Standard ([semver.org](https://semver.org)) ist bewusst technologieneutral formuliert und wird von praktisch jedem modernen Paket-Ökosystem verwendet:

```
Rust      -> Cargo / crates.io           (SemVer ist dort sogar Teil der offiziellen Doku)
Python    -> pip / PyPI                  (PEP 440, SemVer-kompatibel, aber etwas allgemeiner)
PHP       -> Composer / Packagist
Ruby      -> RubyGems / Bundler
Java      -> Maven / Gradle              (Konvention, nicht technisch erzwungen)
Go        -> Go-Module (go.mod)          (SemVer ist hier sogar Teil des Toolings selbst)
Swift     -> Swift Package Manager
.NET      -> NuGet
```

- Wer einmal `^1.2.3` und `~1.2.3` verstanden hat, versteht damit auch den Kern der Versionierung in fast jedem anderen Ökosystem.

## Auch jenseits von klassischen Paketmanagern

- **Docker / OCI-Images**: Tags wie `myapp:2.4.1` folgen oft freiwillig SemVer, technisch erzwungen wird das aber nicht - ein Tag ist letztlich nur Text.
- **Helm-Charts** (Kubernetes): `Chart.yaml` verlangt explizit eine SemVer-2.0-konforme `version`.
- **APIs**: Viele REST-/GraphQL-APIs verwenden SemVer-ähnliche Versionsnummern in der URL oder im Header (`/api/v2/...`), meist aber nur grob an MAJOR orientiert.
- **Browser und Betriebssysteme**: Chrome, Firefox, Node.js selbst - alle verwenden SemVer oder sehr ähnliche Schemata für ihre eigenen Releases.
- **Go** geht besonders weit: Ab MAJOR-Version 2 muss sich sogar der **Modul-Pfad** ändern (`example.com/mod/v2`) - eine inkompatible Änderung ist dort im wahrsten Sinne Teil der Adresse.
