
# 9.7 HTTP, APIs und Server State / Fehlerbehandlung in HTTP-Aufrufen

## Fehlerbehandlung in HTTP-Aufrufen

- Fehler sind in 2 Kategorien unterteilt: Client-Fehler und Server-Fehler.
- Wenn der Server einen Statuscode zurückgibt, der mit 2xx beginnt, war die Anfrage erfolgreich, ansonsten gibt es einen Fehler auf der Serverseite.
- Ein Server-Fehler ist aber KEIN(!) Fehler per se, sondern eine Antwort des Servers auf eine Anfrage und es ist Interpretationssache, ob es sich um einen Fehler handelt.
- Beispiel: Ein 404-Statuscode bedeutet, dass die angeforderte Ressource nicht gefunden wurde und das muss nicht unbedingt ein Fehler sein. Schließlich könnte der Client absichtlich eine nicht vorhandene Ressource anfordern.

# 9.7 HTTP, APIs und Server State / Fehlerbehandlung in HTTP-Aufrufen

## Fehlerbehandlung in HTTP-Aufrufen bei Promises und Fetch-API

- Bei Promises können Fehler mit `.catch()` abgefangen werden.
- Bei Async/Await können Fehler mit `try/catch` abgefangen werden.

- Um aufzuräumen gibt es bei Promises den Handler `.finally()`, der immer ausgeführt wird, egal ob die Anfrage erfolgreich war oder nicht.
- Um aufzuräumen gibt es bei Async/Await den `finally`-Block, der immer ausgeführt wird, egal ob die Anfrage erfolgreich war oder nicht.

- Beispiel mit Async/Await:

```typescript
async function fetchData() {
    try {
        const response = await fetch('https://api.example.com/data')
        const data = await response.json()
        console.log(data)
    } catch (error) {
        // Achtung: Eine 404- oder 500-Antwort ist KEIN Fehler, sondern eine Antwort des Servers und man würde nicht hier landen.
        console.error('Error:', error)
    } finally {
        console.log('Cleanup')
    }
}
```

# 9.7 HTTP, APIs und Server State / TanStack Query – Motivation

## Warum TanStack Query?

- Das manuelle Laden von Daten mit `useEffect` und `useState` hat viele Tücken:
  - Kein eingebautes Caching – bei jeder Navigation wird neu geladen
  - Kein automatisches Refetching bei Fokuswechsel oder Netzwerkreconnect
  - Loading- und Error-Zustände müssen selbst verwaltet werden
  - Race Conditions sind schwer zu vermeiden
  - Kein De-Duplikation gleichzeitiger Anfragen

- TanStack Query (früher React Query) löst all diese Probleme mit einem einzigen Hook: `useQuery`.

- Installation:

```bash
npm install @tanstack/react-query
```


# 9.7 HTTP, APIs und Server State / TanStack Query – Grundkonzepte

## Kernkonzepte

- **Query**: eine Anfrage zum Laden von Daten, identifiziert durch einen `queryKey`
- **Mutation**: eine Anfrage zum Verändern von Daten (POST, PUT, DELETE) via `useMutation`
- **QueryClient**: der zentrale Cache, der alle Queries verwaltet
- **QueryClientProvider**: stellt den `QueryClient` per Context der gesamten App zur Verfügung

- TanStack Query unterscheidet zwischen:
  - **stale** (veraltet): die Daten sind gecacht, könnten aber neu geladen werden
  - **fresh** (frisch): die Daten wurden kürzlich geladen und gelten als aktuell
  - **loading / fetching / error / success**: Zustandsmaschine pro Query


# 9.7 HTTP, APIs und Server State / TanStack Query – Setup

## QueryClientProvider einrichten

```typescript
// main.tsx
import { QueryClient, QueryClientProvider } from '@tanstack/react-query'

const queryClient = new QueryClient()

ReactDOM.createRoot(document.getElementById('root')!).render(
    <QueryClientProvider client={queryClient}>
        <App />
    </QueryClientProvider>
)
```

- Der `QueryClient` nimmt optional eine Konfiguration entgegen, z. B. `defaultOptions` für `staleTime` oder `gcTime`.


# 9.7 HTTP, APIs und Server State / TanStack Query – useQuery

## useQuery – Daten laden

```typescript
import { useQuery } from '@tanstack/react-query'

type Quote = { id: number; quote: string; author: string }

function Quotes() {
    const { data, isLoading, isError, error } = useQuery({
        queryKey: ['quotes'],
        queryFn: async () => {
            const res = await fetch('https://dummyjson.com/quotes')
            if (!res.ok) throw new Error('Netzwerkfehler')
            return res.json() as Promise<{ quotes: Quote[] }>
        },
    })

    if (isLoading) return <p>Laden…</p>
    if (isError)   return <p>Fehler: {error.message}</p>

    return (
        <ul>
            {data?.quotes.map(q => <li key={q.id}>{q.quote} – {q.author}</li>)}
        </ul>
    )
}
```

- `queryKey` ist ein Array und dient als Cache-Schlüssel – ändert sich ein Wert darin, wird die Query neu ausgeführt.


# 9.7 HTTP, APIs und Server State / TanStack Query – useMutation

## useMutation – Daten verändern

```typescript
import { useMutation, useQueryClient } from '@tanstack/react-query'

function AddQuote() {
    const queryClient = useQueryClient()

    const mutation = useMutation({
        mutationFn: async (newQuote: { quote: string; author: string }) => {
            const res = await fetch('https://dummyjson.com/quotes/add', {
                method: 'POST',
                headers: { 'Content-Type': 'application/json' },
                body: JSON.stringify(newQuote),
            })
            if (!res.ok) throw new Error('Fehler beim Speichern')
            return res.json()
        },
        onSuccess: () => {
            // Cache für 'quotes' ungültig machen → automatisches Neu-Laden
            queryClient.invalidateQueries({ queryKey: ['quotes'] })
        },
    })

    return (
        <button onClick={() => mutation.mutate({ quote: 'Hello', author: 'World' })}>
            {mutation.isPending ? 'Speichert…' : 'Hinzufügen'}
        </button>
    )
}
```


# 9.7 HTTP, APIs und Server State / TanStack Query – Custom Hooks

## Custom Hooks für API-Zugriffe anlegen

- Eine bewährte Praxis ist es, `useQuery` und `useMutation` in eigene Custom Hooks zu kapseln.
- Dadurch werden Komponenten von der Datenbeschaffungslogik entkoppelt.
- Der `queryKey` und die `queryFn` werden an einem zentralen Ort definiert.

```typescript
// hooks/useQuotes.ts
import { useQuery, useMutation, useQueryClient } from '@tanstack/react-query'

export function useQuotes() {
    return useQuery({
        queryKey: ['quotes'],
        queryFn: async () => {
            const res = await fetch('https://dummyjson.com/quotes')
            if (!res.ok) throw new Error('Fehler beim Laden')
            return res.json() as Promise<{ quotes: Quote[] }>
        },
        staleTime: 1000 * 60 * 5, // 5 Minuten frisch
    })
}

export function useAddQuote() {
    const queryClient = useQueryClient()
    return useMutation({
        mutationFn: (q: { quote: string; author: string }) =>
            fetch('https://dummyjson.com/quotes/add', {
                method: 'POST',
                headers: { 'Content-Type': 'application/json' },
                body: JSON.stringify(q),
            }).then(r => r.json()),
        onSuccess: () => queryClient.invalidateQueries({ queryKey: ['quotes'] }),
    })
}
```


# 9.7 HTTP, APIs und Server State / TanStack Query – Custom Hooks Verwendung

## Verwendung der Custom Hooks in Komponenten

```typescript
import { useQuotes, useAddQuote } from './hooks/useQuotes'

export function QuotesPage() {
    const { data, isLoading, isError } = useQuotes()
    const addQuote = useAddQuote()

    if (isLoading) return <p>Laden…</p>
    if (isError)   return <p>Fehler beim Laden der Zitate.</p>

    return (
        <div>
            <ul>
                {data?.quotes.map(q => <li key={q.id}>{q.quote}</li>)}
            </ul>
            <button onClick={() => addQuote.mutate({ quote: 'Neu', author: 'Anon' })}>
                Hinzufügen
            </button>
        </div>
    )
}
```

- Die Komponente weiß nichts über Fetch, Cache oder Fehlerbehandlung – das übernimmt der Custom Hook.
- Mehrere Komponenten können denselben Hook verwenden und profitieren automatisch vom gemeinsamen Cache.


# 9.7 HTTP, APIs und Server State / Typsicherheit mit Zod

## Zod – Schema-Validierung zur Laufzeit

- `fetch` und `axios` liefern `any` zurück – TypeScript-Typen gelten nur zur Compile-Zeit.
- Zod ermöglicht es, die Antwort eines APIs zur **Laufzeit** gegen ein Schema zu validieren.
- Dadurch werden unerwartete API-Antworten sofort als Fehler sichtbar, statt still falsche Daten anzuzeigen.

```bash
npm install zod
```

```typescript
import { z } from 'zod'

const QuoteSchema = z.object({
    id:     z.number(),
    quote:  z.string(),
    author: z.string(),
})

const QuotesResponseSchema = z.object({
    quotes: z.array(QuoteSchema),
})

export type Quote = z.infer<typeof QuoteSchema>

// Im queryFn:
queryFn: async () => {
    const res  = await fetch('https://dummyjson.com/quotes')
    const json = await res.json()
    return QuotesResponseSchema.parse(json) // wirft bei Abweichung einen Fehler
}
```


# 9.7 HTTP, APIs und Server State / API-Client-Generierung mit hey-api

## hey-api – OpenAPI → TypeScript Client

- hey-api (früher `openapi-typescript-codegen`) generiert aus einer OpenAPI-Spezifikation automatisch:
  - TypeScript-Typen für alle Request- und Response-Objekte
  - Fertige `fetch`- oder `axios`-basierte Client-Funktionen
  - Optional: TanStack-Query Hooks direkt aus dem OpenAPI-Schema

- Installation und Codegenerierung:

```bash
npm install @hey-api/openapi-ts --save-dev
npx openapi-ts --input https://api.example.com/openapi.json --output src/client
```

- Das Ergebnis ist ein vollständig typisierter API-Client, den man direkt in Custom Hooks einsetzen kann:

```typescript
import { getQuotes } from './client/services'  // generiert von hey-api

export function useQuotes() {
    return useQuery({
        queryKey: ['quotes'],
        queryFn: () => getQuotes(),  // typsicher, kein fetch-Boilerplate
    })
}
```

- Vorteil: Änderungen in der API-Spezifikation führen sofort zu Compile-Fehlern im Client-Code.
- Zusammenspiel: **OpenAPI-Spec → hey-api → TypeScript-Client → Custom Hook mit TanStack Query → Komponente**
