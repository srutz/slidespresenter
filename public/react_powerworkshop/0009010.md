# 9.10 HTTP, APIs und Server State / TanStack Query: Queries

## useQuery mit TypeScript

```typescript
import { useQuery } from '@tanstack/react-query'

type Todo = { id: number; todo: string; completed: boolean }
type TodosResponse = { todos: Todo[] }

async function fetchTodos(): Promise<Todo[]> {
    const res = await fetch('https://dummyjson.com/todos?limit=10')
    if (!res.ok) throw new Error(`HTTP ${res.status}`) // fetch wirft bei 4xx/5xx nicht selbst
    const json: TodosResponse = await res.json()
    return json.todos
}

export function TodoList() {
    const { data, isPending, isError, error } = useQuery({
        queryKey: ['todos'],
        queryFn: fetchTodos,
    })

    if (isPending) return <p>Laden…</p>
    if (isError) return <p role="alert">Fehler: {error.message}</p>

    return <ul>{data.map(t => <li key={t.id}>{t.todo}</li>)}</ul>
}
```

- `queryFn` muss ein Promise liefern und bei Fehlern **werfen**.
- Nach den Prüfungen auf `isPending` und `isError` ist `data` typsicher vorhanden.

## Status: isPending, isFetching, isError

- `isPending`: noch keine Daten im Cache (erstes Laden). In v5 der Nachfolger von `isLoading` aus v4.
- `isFetching`: irgendein Request läuft, auch ein Hintergrund-Refetch bei vorhandenen Daten.
- `isLoading`: `isPending && isFetching`, also erstes Laden mit laufendem Request.
- `isError` / `error`: der letzte Versuch ist fehlgeschlagen (nach Retries, Standard: 3 Versuche mit Backoff).
- `status` (`'pending' | 'error' | 'success'`) lässt sich wie die Discriminated Union aus 9.5 verwenden.
- Typisch: Daten anzeigen und bei `isFetching` einen kleinen Spinner zeigen, statt die Liste auszublenden.

## Query Keys

- Der `queryKey` ist ein Array und identifiziert die Daten im Cache. Er muss alle Variablen enthalten, von denen die `queryFn` abhängt.
- Ändert sich ein Wert im Key, wird automatisch eine neue Query geladen (analog zur Dependency-Liste von `useEffect`).
- Konvention: vom Allgemeinen zum Speziellen.

```typescript
useQuery({ queryKey: ['todos'], queryFn: fetchTodos })                      // Liste
useQuery({ queryKey: ['todos', { completed }], queryFn: () => fetchTodos(completed) }) // gefiltert
useQuery({
    queryKey: ['todos', id],                                                 // Detail
    queryFn: () => fetchTodo(id),
    enabled: id !== undefined,                                               // nur laden, wenn id bekannt
})
```

- Keys werden strukturell verglichen, die Reihenfolge von Objekt-Eigenschaften spielt keine Rolle.
- Gemeinsames Präfix `['todos']` erlaubt später, alle zugehörigen Queries gemeinsam zu invalidieren.

## useSuspenseQuery

- Gleiche Optionen wie `useQuery`, aber das Laden und der Fehlerfall werden **nicht in der Komponente** behandelt.
- Solange keine Daten da sind, „suspendiert“ die Komponente: React zeigt das `fallback` der nächsten `<Suspense>`-Grenze.
- Schlägt die `queryFn` fehl, wird der Fehler geworfen und von der nächsten **Error Boundary** gefangen.

```tsx
import { Suspense } from 'react'
import { useSuspenseQuery } from '@tanstack/react-query'
import { ErrorBoundary } from 'react-error-boundary'

function TodoList() {
    const { data } = useSuspenseQuery({     // data ist immer Todo[], nie undefined
        queryKey: ['todos'],
        queryFn: fetchTodos,
    })

    return <ul>{data.map(t => <li key={t.id}>{t.todo}</li>)}</ul>
}

export function TodoPage() {
    return (
        <ErrorBoundary fallback={<p role="alert">Fehler beim Laden</p>}>
            <Suspense fallback={<p>Laden…</p>}>
                <TodoList />
            </Suspense>
        </ErrorBoundary>
    )
}
```

- Die Komponente enthält nur den Erfolgsfall, `isPending` und `isError` entfallen.

## useQuery vs. useSuspenseQuery: Unterschiede

| | `useQuery` | `useSuspenseQuery` |
|---|---|---|
| Ladezustand | `isPending` in der Komponente | `<Suspense fallback>` darüber |
| Fehlerzustand | `isError` / `error` in der Komponente | Error Boundary darüber |
| Typ von `data` | `T \| undefined` bis zur Prüfung | immer `T` |
| `status` | `'pending' \| 'error' \| 'success'` | nur `'success'` (sonst wird geworfen) |
| `enabled` (abhängige Query) | ja | nein |
| `placeholderData` | ja | nein |
| Mehrere Queries | laufen parallel | in **einer** Komponente nacheinander (Waterfall) |
| Key-Wechsel | alte `data` bleibt mit `isFetching` sichtbar | suspendiert erneut, Fallback erscheint |

- Cache, `staleTime`, Retries, Refetching und Invalidation funktionieren identisch, es ist derselbe Query-Cache.
- Hintergrund-Refetches suspendieren nicht, nur das erste Laden (und ein neuer Key ohne Cache-Eintrag).

## useSuspenseQuery: Vor- und Nachteile

**Vorteile**

- Weniger Code und weniger Verzweigungen: Komponenten beschreiben nur den Erfolgsfall.
- `data` ist ohne Narrowing typsicher, kein `undefined` und kein `!`.
- Lade- und Fehlerbehandlung liegen zentral an Grenzen, gemeinsam für ganze Teilbäume.
- Passt zu Concurrent Features: `useTransition`, `startTransition` und `use` aus React 19.

**Nachteile**

- **Waterfalls:** zwei `useSuspenseQuery` in derselben Komponente laden nacheinander. Lösung: `useSuspenseQueries` oder Daten vorab laden (`prefetchQuery`, Router-Loader).
- Keine abhängigen Queries über `enabled`, stattdessen aufteilen oder verschachteln.
- Ein neuer Key lässt das Fallback wieder aufblitzen. Abhilfe: Key-Änderung in `startTransition` / `useTransition` packen.
- Fehler brauchen eine Error Boundary, für „Erneut versuchen“ zusätzlich `QueryErrorResetBoundary`.
- Feinere Granularität (Spinner pro Widget) erfordert mehr `<Suspense>`-Grenzen und damit mehr Überlegung beim Layout.

**Faustregel:** `useSuspenseQuery` für Daten, ohne die die Komponente nichts anzeigen kann. `useQuery` bei optionalen, abhängigen oder teilweise sichtbaren Daten.
