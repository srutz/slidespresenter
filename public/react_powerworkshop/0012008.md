# 12.8 State Management mit Zustand / Zustand: Asynchrone Actions und DevTools

## Async Actions

- Actions in Zustand dürfen `async` sein. Es gibt keine Thunks oder Extra-Reducer, `set` wird einfach nach dem `await` aufgerufen.
- Ladezustand und Fehler gehören als Felder in den Store.

```typescript
import { create } from 'zustand'

type Todo = { id: number; text: string; done: boolean }

type TodoStore = {
    todos: Todo[]
    loading: boolean
    error: string | null
    loadTodos: () => Promise<void>
}

export const useTodoStore = create<TodoStore>()((set) => ({
    todos: [],
    loading: false,
    error: null,
    loadTodos: async () => {
        set({ loading: true, error: null })
        try {
            const res = await fetch('/api/todos')
            if (!res.ok) throw new Error(`HTTP ${res.status}`)
            set({ todos: await res.json(), loading: false })
        } catch (e) {
            set({ error: e instanceof Error ? e.message : 'Unbekannter Fehler', loading: false })
        }
    },
}))
```

- Für Server-Daten ist TanStack Query meist die bessere Wahl (siehe Kapitel 9 und 12.10).

# 12.8 State Management mit Zustand / Zustand: Asynchrone Actions und DevTools

## devtools-Middleware

- `devtools` verbindet den Store mit der **Redux DevTools** Browser-Extension: State-Inspektion und Time Travel.
- Der dritte Parameter von `set` benennt die Action, sonst erscheint sie als "anonymous".

```typescript
import { create } from 'zustand'
import { devtools } from 'zustand/middleware'

export const useCounterStore = create<CounterStore>()(
    devtools(
        (set) => ({
            count: 0,
            increment: () =>
                set((s) => ({ count: s.count + 1 }), undefined, 'counter/increment'),
            reset: () => set({ count: 0 }, undefined, 'counter/reset'),
        }),
        { name: 'CounterStore', enabled: import.meta.env.DEV }
    )
)
```

- `name` unterscheidet mehrere Stores in den DevTools.
- Mit `enabled: import.meta.env.DEV` ist die Middleware in Produktion abgeschaltet.

## Reihenfolge der Middleware

- Middleware wird geschachtelt, die äußerste wird zuletzt angewendet.
- Empfehlung: `devtools` ganz außen, damit es die Änderungen aller inneren Middleware sieht. Dann `persist`, innen `immer`.
- Bei `immer` in Kombination mit `devtools` werden `set`-Aufrufe wie gewohnt benannt.

```typescript
export const useTodoStore = create<TodoStore>()(
    devtools(
        persist(
            immer((set) => ({
                todos: [],
                addTodo: (text) =>
                    set((state) => {
                        state.todos.push({ id: nextId++, text, done: false })
                    }, undefined, 'todos/add'),
            })),
            { name: 'todo-store' }
        ),
        { name: 'TodoStore' }
    )
)
```

- Wichtig bleibt die Curried-Syntax `create<T>()(...)`.
