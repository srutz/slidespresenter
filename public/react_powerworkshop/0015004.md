# 15.4 Best Practices und Architektur / Client State vs. Server State in der Architektur

## Jede Art von State hat ihren Ort

| Art von State | Beispiel | Werkzeug | Kapitel |
|---|---|---|---|
| Server State | Todos, Produkte vom Backend | TanStack Query | 9 |
| Globaler Client State | Warenkorb, Theme, UI-Filter | Zustand | 12 |
| URL State | Seite, Suchbegriff, Produkt-ID | React Router | 10 |
| Formular-State | Eingaben, Validierungsfehler | React Hook Form + Zod | 11 |
| Lokaler UI-State | Dialog offen, Eingabefeld | `useState` | 7 |

- Server State gehört dem Server; im Client liegt nur ein Cache, der veralten kann (Stale-Time, Invalidierung).
- Client State gehört dem Browser und hat keine Quelle im Backend.

# 15.4 Best Practices und Architektur / Beispielarchitektur

- Produktliste: Daten per `useQuery`, Suchbegriff und Seite in der URL (`useSearchParams`), damit Links teilbar sind.
- Warenkorb: Zustand-Store, optional mit `persist`-Middleware.
- Neues Produkt anlegen: React Hook Form mit Zod-Schema, Senden per `useMutation`, danach `invalidateQueries`.
- Dialog "Löschen bestätigen": `useState` direkt in der Komponente.

```typescript
// Faustregel bei jeder neuen Information:
// 1. Kommt sie vom Server?             -> TanStack Query
// 2. Soll sie im Link stehen?          -> URL
// 3. Ist sie Teil eines Formulars?     -> React Hook Form
// 4. Brauchen sie mehrere Bereiche?    -> Zustand
// 5. Sonst                             -> useState, so lokal wie möglich
```

- Server-Daten niemals in einen Zustand-Store kopieren: zwei Quellen der Wahrheit laufen auseinander.
