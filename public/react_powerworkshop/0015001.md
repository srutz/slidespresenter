# 15.1 Best Practices und Architektur / Feature-basierte Projektstruktur

## Nach Fachlichkeit statt nach Dateityp gliedern

- Nicht: ein riesiger Ordner `components/`, ein Ordner `hooks/`, ein Ordner `utils/` für die ganze Anwendung.
- Besser: ein Ordner pro Feature (`todos`, `products`, `auth`), der alles Zugehörige bündelt.
- Pro Feature: `components/`, `hooks/`, `api/`, `types.ts` und ein `index.ts` als öffentliche Schnittstelle.
- Was von mehreren Features genutzt wird, wandert nach `shared/` (z. B. `shared/ui` für Button, Dialog, Input).
- Vorteil: Ein Feature lässt sich verstehen, ändern, testen und löschen, ohne die ganze Anwendung zu kennen.

# 15.1 Best Practices und Architektur / Beispielbaum der Seminaranwendung

```bash
src/
  app/                 # Einstieg: Router, Provider, QueryClient
    App.tsx
    routes.tsx
  features/
    todos/
      api/todos-api.ts
      components/TodoList.tsx
      components/TodoForm.tsx
      hooks/useTodos.ts
      types.ts
      index.ts         # öffentliche API des Features
    products/
      ...
  shared/
    ui/Button.tsx
    hooks/
    lib/http.ts
  main.tsx
```

# 15.1 Best Practices und Architektur / Import-Regeln

- Abhängigkeitsrichtung: `app` → `features` → `shared`, nie umgekehrt.
- `shared` kennt keine Features; es enthält nur generischen Code.
- Features importieren andere Features nur über deren `index.ts`, nicht über interne Pfade.
- Features sollen sich möglichst nicht gegenseitig kennen; Zusammenspiel passiert in `app` oder auf Seitenebene (Routen, siehe Kapitel 10).
- Pfad-Alias statt `../../..`: in `tsconfig.json` und `vite.config.ts` einrichten (Kapitel 2).

```typescript
// gut
import { TodoList } from '@/features/todos'
// schlecht
import { TodoList } from '@/features/todos/components/TodoList'
```
