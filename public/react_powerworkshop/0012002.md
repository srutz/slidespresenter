# 12.2 State Management mit Zustand / Arten von State

## Nicht jeder State gehört in einen globalen Store

- Der häufigste Fehler: alles in einen globalen Store legen.
- Zuerst fragen: **Wem gehört der State, und wer braucht ihn?**
- Die Art des States bestimmt das passende Werkzeug.

| Art | Beispiel | Werkzeug |
|---|---|---|
| Local State | Dropdown offen, Eingabefeld | `useState`, `useReducer` |
| Global/Client State | Theme, Warenkorb, Auswahl, Filter | Zustand, Redux Toolkit, Context |
| Server State | Produkte, Benutzer, Bestellungen | TanStack Query (Kapitel 9) |
| URL State | Seite, Suchbegriff, Sortierung | React Router (`useSearchParams`) |
| Form State | Eingaben, Fehler, dirty/touched | React Hook Form + Zod (Kapitel 11) |

## Unterschiede im Detail

- **Server State** gehört dem Server: er ist asynchron, kann veralten und wird von mehreren Nutzern geändert. Er braucht Caching, Refetching und Invalidierung.
- **Client State** gehört der Anwendung: synchron, sofort verfügbar, nur im Browser relevant.
- **URL State** ist teilbar und bookmarkbar. Was in der URL stehen kann, sollte dort stehen.
- **Form State** ist kurzlebig und feldweise. Eine Form-Library vermeidet Re-Renders bei jedem Tastendruck.
- Faustregel: Der State wird auf der **niedrigsten** Ebene gehalten, die ihn braucht, und erst bei Bedarf nach oben geschoben.
