0. ZIEL UND LEITFADEN
---------------------------------------------------------------------
Roter Faden (in Folie 16.1 als Stack-Bild):
  React + TS + Vite -> Tailwind -> Router -> Zustand -> TanStack Query
  -> React Hook Form + Zod -> useHooks -> Vitest/RTL/MSW -> Playwright

Leitsatz, den man oft wiederholt:
  "Jeder Baustein löst genau ein Problem."
  Client State  -> useState / Context / Zustand
  Server State  -> TanStack Query
  URL State     -> Router
  Form State    -> React Hook Form + Zod

Grundregeln, die über 3 Tage immer wieder auftauchen:
  1. UI = Funktion(State). State ändern -> React rendert neu.
  2. State nie mutieren, immer neue Objekte/Arrays (Spread).
  3. Abgeleitete Werte beim Rendern berechnen, nicht in State/Effect.
  4. useEffect nur für Synchronisation mit der Außenwelt.
  5. Server-Daten nicht in einen Store kopieren (TanStack Query).
  6. Erst messen, dann optimieren (memo/useMemo/useCallback).

[09:30-11:15] K2 React Einführung (9 Folien, ca. 105')
---------------------------------------------------------------------
Kernaussagen:
- React ist eine UI-Bibliothek, kein Full-Framework (kein Router, kein
  Datenlayer). Deshalb der "Seminar-Stack" aus K16.
- Deklarativ: Man beschreibt, wie die UI zu einem State aussieht.
- Komponenten sind Funktionen, die JSX zurückgeben.
- Alternativen (2.4): Angular, Vue, Svelte, Solid. Gemeinsamkeiten
  betonen (Komponenten, Reaktivität), keine Glaubenskriege.
Demo/Live:
- 2.5: "npm create vite@latest" -> React + TypeScript. Dev-Server starten,
  Dateien durchgehen (index.html, main.tsx, App.tsx, vite.config.ts).
- 2.6 Ordnerstruktur ist die längste Folie (13 KB): nicht vorlesen,
  nur durchscrollen. Wichtig: package.json, lock-Datei, import von Assets,
  Vite-Proxy (2.5) für API-Aufrufe ohne CORS-Ärger.
- React DevTools installieren und Komponentenbaum zeigen.
- JSX (2.8/2.9): Regeln - ein Root-Element/Fragment, className statt
  class, {} für Ausdrücke, Self-Closing-Tags, camelCase-Attribute,
  Kommentare {/* */}. Bedingung: && und Ternary; Listen: map + key.
  JSX wird zu JS kompiliert (kein Template-System!).
Häufige Fragen:
- "Warum className?"  class ist reserviertes JS-Wort.
- "Ist das nicht HTML in JS?"  Nein, Syntax-Zucker für Funktionsaufrufe.
- "CRA?"  Tot/deprecated, deshalb Vite (K17.2 nur Legacy).
Mini-Übung (10'): Hello-World-Seite mit Liste aus Array (map) und
einer bedingten Anzeige.

[11:15-12:30] K3 Komponenten, Props, State - Teil 1 (3.1-3.6)
---------------------------------------------------------------------
Kernaussagen:
- Komponentennamen groß (PascalCase), sonst wird es als HTML-Tag gesehen.
- Props sind read-only, fließen top-down. children = Inhalt zwischen Tags.
- Rendering-Modell (3.1, mehrere Folien + Diagramme): WICHTIGSTER
  Gedanke des Kurses. Render-Phase (Komponenten aufrufen, Virtual DOM
  vergleichen) vs. Commit-Phase (DOM ändern). Auslöser für Re-Render:
  State-Änderung, Eltern rendert neu, Context-Änderung.
- Re-Render heißt NICHT, dass das DOM neu gebaut wird.
Demo/Live:
- Counter mit useState; console.log im Render zeigen.
- Props mit TypeScript typisieren, Destructuring, Default-Werte,
  boolesche Props, children.
- Event-Handler: onClick={handler}  NICHT onClick={handler()}.
Falle: Funktion aufrufen statt übergeben -> Endlosschleife/Warnung.

[13:30-15:00] K3 Teil 2 (3.7-3.12)
---------------------------------------------------------------------
Kernaussagen useState (3.7 ist die zweitlängste Folie):
- Rules of Hooks: nur auf Top-Level, nur in Komponenten/Custom Hooks.
- State-Update ist asynchron/gebündelt: nach setX liest man im selben
  Render noch den alten Wert.
- Funktionsvariante setX(prev => prev + 1), wenn neuer Wert vom alten
  abhängt (Stale-Werte vermeiden, 3x setCount(count+1) = +1 nicht +3).
- Objekte/Arrays: kopieren mit Spread, nie mutieren.
  Array: [...a, x], a.filter(), a.map(); Objekt: {...o, feld: v}.
- Initial-State lazy: useState(() => teureBerechnung()).
- Reset per key: <Form key={id} /> erzwingt frischen State.
- Lifting State Up: gemeinsamen State zum nächsten gemeinsamen Vorfahren.
- Controlled Components / Two-Way-Binding (3.10): value + onChange.
- Listen: key = stabile ID, NICHT Index (siehe 15.9 Anti-Patterns).
- Bedingtes Rendern: &&, Ternary, Early Return.
  Falle: {count && <X/>} rendert bei 0 eine "0".
Übung (25'): Todo-Liste (hinzufügen, abhaken, löschen, Filter).
  Komponenten: TodoList, TodoItem, AddTodo. Callback-Props nach oben.

[15:15-16:30] K4 Tailwind CSS (13 Folien)
---------------------------------------------------------------------
Hinweis: Tailwind ist der Standard des Kurses; 4.10-4.13 (Stylesheets,
Inline, CSS Modules, CSS-in-JS) nur als Einordnung (max. 10').
Kernaussagen:
- Utility-First: Klassen im Markup statt eigener CSS-Dateien.
  Vorteil: kein Naming, kein toter CSS-Code, lokal verständlich.
- Setup mit Vite-Plugin (@tailwindcss/vite) und @import "tailwindcss".
- Mobile-first: unprefixed = alle, md: ab Breakpoint.
- Varianten: hover:, focus:, disabled:, dark:, group-hover:, peer-.
- Dynamische Klassen: Tailwind scannt statisch! NIE "bg-" + color
  zusammenbauen. Stattdessen Lookup-Objekt mit vollständigen Klassen.
  clsx für Bedingungen, tailwind-merge für Konflikte.
- Wiederverwendung durch React-Komponenten (Button, Card, Badge),
  nicht durch @apply.
- Dark Mode (4.9): dark: Variante, @theme für Design Tokens.
Übung (15'): Karten-Grid responsive (1/2/3 Spalten) + Button-Komponente
  mit Varianten (primary/secondary/danger).
Tagesabschluss (5'): Fragen, Ausblick, ggf. Hausaufgabe: Todo-App stylen.

[09:20-10:30] K5 React-Komponenten im Detail (5.1-5.8)
---------------------------------------------------------------------
- 5.3 Composition statt Vererbung: children (Containment), Slots über
  Props (header=, footer=), Specialization. In React erbt man nie.
- 5.4 useEffect (längste Folie von K5):
  * Effekte = Synchronisation mit externen Systemen (Fetch, Timer,
    Subscriptions, DOM-APIs), kein Lifecycle-Ersatz.
  * 3 Varianten: ohne Array (jeder Render), [] (einmal beim Mount),
    [a,b] (bei Änderung).
  * Cleanup-Funktion zurückgeben (Timer, Listener, Abort).
  * Stale Closures und endlose Render-Schleifen (Objekt/Array in
    Dependencies, setState im Effect ohne Bedingung).
  * StrictMode ruft Effekte im Dev doppelt auf -> Absicht! Cleanup testen.
- 5.5 "You Might Not Need an Effect": abgeleitete Werte beim Rendern
  berechnen; Aktionen in Event-Handler; Reset per key.
- 5.6 useRef: Wert ohne Re-Render / Zugriff auf DOM (focus()).
- 5.7 Fragment; 5.8 Context (createContext, Provider, useContext) als
  "Dependency Injection", Nachteil: alle Consumer rendern bei Wertänderung.
Demo: Timer-Komponente mit/ohne Cleanup, StrictMode-Doppelaufruf zeigen.
Übung (20'): Fenstergröße/Dark-Mode-Context bauen.

[11:30-12:30] K6 React mit TypeScript (9 Folien)
---------------------------------------------------------------------
Hinweis: Wer TS schon kennt, schneller durchgehen; bei JS-Teilnehmern
mehr Zeit für 6.2.
- Props: type Props = {...}; Destructuring + Default.
- Events: React.ChangeEvent<HTMLInputElement>, MouseEvent, FormEvent.
- Hooks typisieren: useState<User | null>(null), useRef<HTMLInputElement>(null),
  createContext<Ctx | null>(null) + Guard-Hook.

Falle: "as" Casts umgehen den Compiler - sparsam verwenden.

[13:30-15:00] K7 Hooks und moderne Patterns (20 Folien)
---------------------------------------------------------------------
Nicht alles gleich tief. Gewichtung:
  tief:   useReducer (7.6/7.7/7.11), Custom Hooks (7.12), Anti-Patterns (7.20)
  mittel: useMemo/useCallback (7.8-7.10), useTransition, useDeferredValue
  kurz:   useEffectEvent, useSyncExternalStore, use(), Actions,
          useOptimistic (React-19-Überblick; nicht vertiefen)
Kernaussagen:
- useReducer: wenn mehrere Teilzustände zusammengehören oder Übergänge
  komplex sind. Actions als Discriminated Union, reducer ist reine Funktion.
- useCallback/useMemo: Referenzstabilität, nur mit memo oder als
  Dependency sinnvoll; erst messen (siehe 15.8).
- useTransition: UI bleibt reaktionsfähig bei schwerem Update
  (isPending). useDeferredValue: verzögerte Kopie eines Werts.
- useEffectEvent: aktuellen Wert im Effect lesen ohne neu zu
  synchronisieren. (Neu/stable-Status in der aktuellen Version prüfen!)
- use() (React 19): Promise/Context lesen; Actions + useOptimistic.
- Hook-Anti-Patterns (7.20): Hooks in Bedingungen/Schleifen, fehlende
  Dependencies unterdrücken (eslint-disable), Hooks als Ersatz für
  Funktionen ohne State.
Übung (30'): Custom Hook useLocalStorage oder useFetch, danach mit
  useReducer als Request-State neu bauen.

7. WIEDERKEHRENDE FALLEN UND ANTWORTEN
=====================================================================
- "Mein Effect läuft doppelt." -> StrictMode im Dev, bewusst.
- "State ist nach setX noch alt." -> Update gebündelt; Funktionsform.
- "Liste springt/verliert Eingaben." -> key falsch (Index/Zufall).
- "Komponente rendert ständig neu." -> neues Objekt/Array/Funktion als
  Prop oder Dependency; Effect setzt State ohne Bedingung.
- "Tailwind-Klasse fehlt im Build." -> dynamisch zusammengebaut.
- "Deep-Link 404 in Produktion." -> SPA-Fallback fehlt (K14.5).
- "fetch wirft bei 404 nicht." -> response.ok prüfen.
- "Context macht alles langsam." -> Zustand/Selektoren oder
  Context aufteilen.
- "Brauche ich useMemo überall?" -> Nein; erst messen, React Compiler.
- "Redux oder Zustand?" -> Neu: Zustand/TanStack Query; Redux Toolkit
  für Bestandsprojekte und große Teams.
- "Wann Next.js?" -> SEO, SSR, RSC, Full-Stack; SPA reicht oft für
  interne Tools.
